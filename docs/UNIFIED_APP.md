# Building the unified Cinderdeck app

Cinderdeck is one regular macOS application. Open it from Finder, Spotlight, or the Dock to show its main window. It stays in the Dock and app switcher when windows close; reopening returns to the main window. The native app retains its identity, capture permissions, preferences, global shortcuts, menu/status bar, workspace services, control socket, and Sparkle updater. Its main workspace window is the Cinderdeck React agent shell, with the existing Chromium preview and recording runtime. Native capture, annotation and history tools remain available through that shell. All preferences live inline in its unified Settings interface; native storage, validation and Keychain ownership remain in the parent app. See [PREFERENCES.md](PREFERENCES.md).

The native app launches a private `Contents/Resources/Cinderdeck.app/Contents/MacOS/Cinderdeck` child. This bundle is shipped inside Cinderdeck; it is not a second product to install. Its identifier is `com.ryancardin.cinderdeck.runtime`, while the outer app remains `com.ryancardin.cinderdeck` (`com.ryancardin.cinderdeck.debug` for Debug). The internal bundle does not register URL schemes. Native Cinderdeck owns updates for the entire bundle; the runtime's independent updater is disabled in native-host mode.

## Desktop interface

The main interface is available only inside the macOS application. Packaged builds load their bundled renderer assets through the private `deckhand://app` protocol and ignore inherited `VITE_DEV_SERVER_URL` values. The runtime's HTTP/WebSocket listener remains an API transport for desktop and companion connections. Requests for `/`, settings routes, pairing pages, or renderer files return 404; they do not serve HTML or redirect to a web development server.

For isolated renderer development, `node scripts/dev-runner.ts dev --home-dir /absolute/path/to/disposable-state` starts the desktop runtime with a private Vite renderer. Each launcher generates a credential held by the Electron main process; only its private protocol proxy can request renderer files. Direct browser requests are rejected, and the interface requires the desktop preload bridge before mounting. `--browser` and `--share` are rejected. The legacy `dev:web` invocation selects desktop development. `dev:server` starts only a headless companion API backend. Development data without a selected home or worktree goes into disposable temporary storage. Pairing QR codes and links retain their compatible format as connection data to paste into Cinderdeck or scan with the companion; they do not open a browser interface. Pairing and Tailscale API exposure always target the backend port, including when old state records a renderer URL.

The UI still uses React/Electron as part of the bundled Mac app. This change removes standalone browser access; it does not replace the interface with SwiftUI. Whole-app validation still requires the packaged outer application.

The composer **+** menu can attach the external app you most recently used or a
chosen open window. Browser page metadata is read through Accessibility when
available. Native Cinderdeck tracks app activation and captures the exact selected
window; the runtime receives bounded, correlated metadata and image replies over
the private parent pipe. Suggestions remain in memory, captures stay in the draft
until sent, and app-control permission remains separate. See [Computer use](COMPUTER_USE.md).

## Build and assemble

Clone the Cinderdeck repository normally. The maintained agent runtime source is included as tracked files under `agent-runtime/`, with full history and licenses. Use Xcode 26.2 or later and Rust/Cargo. The builder installs frozen dependencies and bootstraps the supported Node toolchain inside the clone when needed. It does not fetch a different harness revision.

```bash
./scripts/build-unified.sh \
  --output-dir /absolute/path/to/a/delivery-directory \
  --configuration Debug --arch arm64
```

The command runs the runtime's existing desktop artifact builder with `CINDERDECK_NATIVE_SHELL_BUILD=1`, targeting an unpacked macOS app. Node's directory and the runtime's `node_modules/.bin` lead that build's `PATH`. It builds native Cinderdeck at the same time, with the documented Xcode performance-inliner workaround and without an index store, then copies both products into a fresh staging directory and verifies the executable and bundle identifiers before signing.

Debug builds keep the three most recently used runtime builds in `.build/runtime-cache`. A build is reused only when everything that shapes it is unchanged: the runtime checkout's Git-visible files and ignored `.env` files, the Node, Rust and Swift toolchains, the architecture, the `DECKHAND_`, `VITE_`, `EXPO_PUBLIC_`, `CSC_`, `APPLE_`, `APP_VERSION` and `NODE_OPTIONS` environment, the build scripts, and the commit and dirty state embedded for About. A native-only change therefore skips the runtime build. A new commit rebuilds the runtime once. Release builds always rebuild it. Pass `--no-runtime-cache` or set `CINDERDECK_RUNTIME_CACHE=0` to force a rebuild.

To assemble already-built products for manual validation, supply either or both prebuilt apps:

```bash
./scripts/build-unified.sh \
  --output-dir /absolute/path/to/a/fresh-delivery-directory \
  --configuration Debug --arch arm64 \
  --native-app '/absolute/path/to/Cinderdeck Debug.app' \
  --runtime-app /absolute/path/to/Cinderdeck.app
```

The inputs are copied; they are not modified. Missing prebuilt products are built normally. `--arch` accepts `arm64`, `x64`, or `universal`, and supplied products must contain the requested architecture. `--dry-run` validates inputs and prints the plan without building, copying, or signing. Existing output apps are refused. A failed build retains its staging directory and logs for inspection.

This command does not install, launch, replace a live app, reset permissions, create a certificate, or publish an update. It produces one app for manual validation. `build_and_run.sh` and `install-local.sh` use this same packager by default. `--runtime-source` is an optional maintainer override, never a prerequisite for a clone.

## Signing

Debug defaults to ad-hoc signing for disposable manual output. Such builds do not establish a persistent permission identity. To preserve a local certificate identity, explicitly provide an existing identity through `--signing-identity` or `CINDERDECK_SIGNING_IDENTITY`. Release requires an exact existing certificate name or SHA-1 fingerprint; it refuses ad-hoc signing and does not create a missing certificate.

```bash
./scripts/build-unified.sh \
  --output-dir /absolute/path/to/a/fresh-release-directory \
  --configuration Release --arch arm64 \
  --signing-identity 'Your Existing Code Signing Identity'
```

`CINDERDECK_SIGNING_KEYCHAIN` selects an existing keychain; it defaults to the login keychain. The packager signs nested Mach-O code and bundles inside-out, first the runtime, then native helpers including Sparkle, then the outer app. It preserves existing helper entitlements, permits Electron's executable memory, and resolves the native entitlement bundle-ID variables for the selected configuration. Local/ad-hoc identities require library-validation exceptions for the internal Electron runtime and native Sparkle loading. Apple-issued signatures retain the declared entitlements without adding that local exception.

The completed bundle and its runtime receive strict recursive signature checks. Release also requires a certificate-based designated requirement. Local signing uses `--timestamp=none`. Distribution sets `CINDERDECK_SIGNING_TIMESTAMP=--timestamp` for Developer ID signatures, including nested runtime code. This command does not notarize, assess Gatekeeper acceptance, generate a signed Sparkle feed, or validate a public release. Follow the release/signing procedures separately before distribution.

## Runtime and authority boundaries

The native host passes the exact running control socket, current installation identity, and `development` or `release` channel to its owned child. Agent state lives in `AgentRuntime` below that native control directory, with a separate `Profile` subdirectory. Previous standalone runtime databases and native capture history retain their own storage. Provider authentication stays with the configured CLI; a separate agent data directory is not an authentication sandbox or a credential migration.

Parent-to-child route/activate/quit messages use the captured process's stdin. Child readiness, user Quit requests, and allowlisted native-tool requests use bounded stdout markers. Workspace routes are checked against the current native catalog; no arbitrary URLs, paths, or executable commands are accepted. Native Quit retains its running-work confirmation and waits for the captured child to close its backend pool. It does not terminate processes by name or discover unrelated PIDs.

Native-tool requests can open workspace/lane-map, history, preferences, capture, recording, annotation, or updates. The `workspace-setup` surface opens the existing discovery and project-check wizard without a selected workspace. `workspace-editor` requires an exact source workspace ID: no mode opens the inline inspector in **Settings → Workspaces**, while `services`, `tasks`, or `workflows` opens its advanced configuration in the same unified inspector. The `delete` mode opens the same inline settings inspector and its named deletion confirmation; it never deletes without that user confirmation. Workspace headers and Settings → Workspaces expose **Delete workspace…**, with the same action at the bottom of workspace settings. The native workspace header’s **Open in Cinderdeck** button brings the selected workspace or lane and current section into the existing main app window, dismissing the auxiliary workspace tool. The editor refuses lane snapshots instead of editing an inferred owner. The sidebar gear explicitly opens source workspace settings, including from a lane. Workspace and conversation headers also expose labeled settings and **Switch branch…** controls. The `workspace-branches` surface requires an exact workspace or lane ID and no mode or command; it opens the existing native multi-repository branch picker with its changes review and service checks. `execution-map` requires an exact workspace or lane ID and opens the full native task/workflow/process visualization. These tools reuse the existing native supervisor and editor sheets; workspace settings stays in the main settings shell, while finishing project setup returns focus to the same main-app route. `agent-access` requests, and the native Agent access buttons, open **Settings → Integrations → MCP & skills** in the main window, where MCP registration, skills and the Claude Code mod are managed through the `agents.setup` integration capability. Closing other native workspace tools also returns there. Capture modes and preference categories are explicitly validated. The `preferences` surface routes to the matching unified settings page and never opens a separate native preferences window. Native settings reads and saves use a bounded, UUID-correlated private parent-pipe protocol accepted only from the trusted main renderer, with stale-edit validation and confirmed save replies. A recording opened with an exact workspace selects that workspace's native recording log scope. Actual capture and permission requests remain user actions. The backend socket UI method additionally requires the current installation identity and the private live-shell capability; that capability is not a renderer/provider credential. These UI methods do not add provider MCP permissions or general command execution.

The main sidebar lists source workspaces with ordinary sessions directly beneath them. Selecting a workspace leaves its disclosure state unchanged; workspaces start collapsed, and their arrows explicitly show or hide sessions. Sub-agent groups also start collapsed; their arrows expand each level independently. Opening an exact sub-agent in a visible session list reveals only its ancestor path. Expand a workspace, select a session, or press the workspace's plus button to open a new chat with saved defaults. The list combines regular project threads and saved checkout bindings, deduplicates thread IDs, preserves removed-checkout history, and pages older saved sessions. Sub-agent sessions nest under their immediate parent in both lists, with disclosure arrows and independent links, provider icons, status and colors; forks remain independent conversations. Codex native children with a real provider thread also use the ordinary composer: send follow-ups, steer the active child, queue and edit messages, and stop its turn. Other provider-native tasks retain their status bar when the provider does not expose an independently addressable conversation. Pinned sessions appear first in a collapsible **Pinned** section. Pinning or repinning a session moves it to the top and opens the section. A pinned sub-agent stays with its parent conversation. Unpinned sessions default to newest first by when they started, regardless of later activity. Drag a session’s grip to reorder its sibling group; a main session moves with its children, and sub-agents reorder within their immediate parent. Keyboard users can focus the grip, press Space, move with the arrow keys, and press Space again to drop or Escape to cancel. New sessions appear below pins and any leading rows explicitly dragged into place. Neighboring rows captured in a saved arrangement do not gain manual priority over new sessions. Existing whole-list saved orders retain their relative positions among older sessions while new threads appear ahead of them. Each drop records the moved row and a stable creation-time boundary separately from the displayed arrangement, preserving hidden history when archive filters or paging change. Provider icons resolve from each session's execution computer, including custom provider instances and saved conversations. The saved order is shared by the sidebar and full Sessions view, scoped to the workspace, execution computer and installation. Search, paging and archive filters preserve hidden sessions’ saved positions. Each expanded workspace shows ten main session rows and their sub-agents. When pins exist, the Pinned heading occupies one row, leaving nine regular sessions; expanding Pinned reveals all pins without consuming the regular-session allowance. Its disclosure state persists, while navigating to a hidden pin reveals it. A selected regular group outside the limit stays visible when needed; **Show more** opens its searchable Sessions view. Search retains matching descendants with their ancestors, and navigation reveals the selected child’s parent path. Active children retain archived ancestors for context; children with unavailable parents stay accessible and labeled as sub-agents. Right-click any session for **Highlight color…**, with presets, a custom color and **Use default** to clear it. Session colors persist per execution computer and installation alongside workspace sidebar preferences. **Settings → Appearance → Sidebar highlights** edits the ten presets used by workspace, session and sub-agent color pickers. The palette saves locally to this app’s client settings; editing or resetting it does not change highlights already assigned to rows. Pinning, renaming, unread state, archive and deletion use the existing thread actions. Sessions stay accessible while native operational tools reconnect.

Conversations share one mounted shell with the persistent workspace tree; there is no second lane/session sidebar. Workspace sections are Sessions, Services, Tasks, Workflows, Runs, Recordings and Pull requests. Lane creation, lifecycle controls, lane map, lane names, repository lane defaults and ownership transition settings are removed from the active product flow. Old checkout links resolve to their source workspace's sessions. Internal route, wire and persisted identifiers remain compatible.

Git/checkpoint operations use ordinary repository semantics without native checkout reservations or ownership gates. Provider admission resolves the thread's actual working folder and preserves explicit read-only access. Saved native generations and disconnected service tooling do not block a writable session. Worktree handoffs create/select ordinary Git worktrees, update the thread directory and detach its provider before continuing; they do not invoke native lane creation. Worktrees do not assign native service ports automatically. Legacy checkout records and CLI lifecycle methods remain for existing history and scripts.

Native Cinderdeck remains the only owner of workspace/lane service processes, ports, operational logs, runs, and native recordings. The agent runtime owns its threads, provider sessions, chat, diffs, optional Git worktrees and Chromium preview lifecycle. Shared-service aliases carry their actual owner workspace and optional canonical service target; a lane does not acquire a separate owner merely because it displays a shared service. Agents can share workspaces, lanes, and checkouts without claims or writer reservations. Local provider sessions still require installed, authenticated CLIs and their advertised capabilities. This packaging command does not sign in providers, grant third-party access, or prove their live behavior.

## Maintaining the app

The runtime in `agent-runtime/` is owned and maintained as part of Cinderdeck. Workspace packages use `@cinderdeck/*`; the runtime is a private child bundle with no independent release feed. There is no upstream subtree update, patch allowlist, vendor website, or relay deployment in this repository. Preserve the original MIT license and copyright notices for incorporated source.

Update the runtime and native host together, then rebuild, sign, and validate the complete outer app. Provider protocol identifiers, internal `deckhand` module paths, and persisted storage keys remain compatibility details; renaming product labels does not justify moving user databases.

Compilation and signature verification do not prove the integrated product. Manually validate one main window, exact workspace/lane navigation, native tool entry points, provider selection and resumed conversations, preview/recording, shared-service ownership, relaunch, and cancellation/graceful quit. The Debug preview harness scopes operational files, capture output and processing, history database/thumbnails, recording metadata/audio and annotation sidecars to `CINDERDECK_STACKS_PREVIEW_ROOT`. Volatile fixture defaults enable saving and history while disabling clipboard copying. They do not redirect every persistent Debug preference write. Keep that distinction explicit when conducting manual checks.

## Runtime maintenance provenance

`agent-runtime/upstream-integration.json` records the last complete source baseline, the exact target examined, and individually incorporated changes. Selected ports do not advance `integratedThrough`; advance it only after reviewing every applicable change through a target. This is provenance, not an upstream patch gate or synchronization policy.

Run `python3 scripts/check-repository.py` to check ownership boundaries, package identities and repository branding, including candidate files before they are committed. `scripts/check-branding.py` also rejects removable source paths, lower-case product identifiers, help text and demo URLs. Its regression tests run with `python3 -m unittest discover -s scripts/tests`.

The branding audit retains original licenses, copyright and third-party notices; recorded provider transcripts and generated protocol schemas; stored keys, database names, the provider compatibility field `t3CodeRange`, project schema URLs, theme IDs, URI schemes and credential owners; historical MCP aliases and archive layouts; Expo/Fabric native module registration names and their source paths; and exact source provenance or vendor-source refusal guards. These are technical compatibility or attribution data. Ordinary modules, symbols, sample repositories, Maven groups and diagnostic labels use Cinderdeck names. Exact existing launcher/archive lines, checkpoint refs, API/OAuth/clipboard/RPC tokens and storage prefixes retain compatibility. Legal exceptions are exact author lines, never arbitrary copyright-looking product text. Exceptions do not exempt adjacent product copy. Generated icon and bundle identities remain checked by the icon exporter and whole-app packaging verifier.
