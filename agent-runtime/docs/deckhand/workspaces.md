# Working in a Cinderdeck workspace

**Settings → Workspaces** lists each source workspace once. Expand **Folders & files** to inspect its primary checkout, or **Lanes** to see its parallel checkouts and branches. **Workspace settings** edits the parent workspace; **Manage lanes** opens its lane map, and each lane's **Open** link selects that exact checkout. Workspace pages count only source workspaces, while expanded lane lists paginate independently. Disconnected lists remain visible as last observed, with editing and lane navigation unavailable until refreshed.

Use the **gear beside the plus and star** in the sidebar to open that workspace's settings. A lane's gear opens its source workspace settings; it does not edit a lane snapshot. **Workspace settings** also appears in the workspace and conversation headers. Settings manage folders, files, lane defaults and the workspace definition. These native tools are available on the workspace's own Mac.

Right-click a workspace or lane in the sidebar and choose **Highlight color…** for a compact palette of ten colors. Choose a swatch to apply it immediately, use **Custom…** for any color, or **Use default** to restore its original appearance. Each row has its own subtle tint, accent edge and matching icon. Colors persist on this client per execution computer and installation, alongside sidebar order and favorites. Keyboard users can open the same menu with Shift+F10.

Right-click a lane in the sidebar and choose **Delete lane…** to review its removal. Worktrees and files are kept by default; you can choose to delete eligible managed worktrees and explicitly include ignored files. Adopted and shared worktrees, branches, logs, and conversation history are kept. Changed source files and active work can block deletion. Once the selected lane is removed, its source workspace opens; deleting another lane keeps your current view.

Choose **Delete workspace…** in a primary workspace's header, **Settings → Workspaces**, or the deletion section at the bottom of **Workspace settings**. The native confirmation names the workspace and keeps project files, Git branches, logs, and saved runs. Stop services and finish or cancel active runs, then remove or release lanes before deleting. Dependent workspace references also block deletion. Changes made after the settings window opened require reopening it before deletion; failures keep the settings open with an explanation.

Use **Switch branch…** in the workspace or conversation header to open the native branch picker for the selected workspace or lane. It shows the repositories affected and uses the existing changes review and service checks. The branch control in a conversation also supports switching and creating branches; its tooltip says **Switch branch**. Use lanes when you want separate working folders for parallel branches.

Git checks the live workspace and physical checkout identity before changes. Editing settings or reloading a workspace no longer blocks Git merely because an older conversation has the previous native generation. A saved sibling lane whose folder and Git worktree registration are both gone no longer blocks branch changes in a verified checkout; its saved history remains available. If any relevant repository in that lane still exists or retains a Git registration, its ownership checks still apply. A transient workspace connection failure gets one refresh and a new inspection before Git runs; a Git operation is never automatically replayed. Pending ownership moves, replaced checkouts and unverifiable linked worktrees remain blocked. The error identifies the recovery needed, and conversation branch errors expose **Refresh workspace connection** and **Check ownership changes**. For pending moves, expand **Settings → Integrations → Worktree management** and check the original saved operation. Refreshing does not resolve an uncertain move or repair Git registrations.

Open Workspaces and select a workspace. New feature creates an independent native lane and starts a conversation with all its workspace folders. Choose a new branch, provider, title and objective; optionally override each repository’s start revision, run setup, or start the lane’s services. Setup is enabled by default and services remain stopped unless selected. New lane remains available for creating a checkout without an agent.

To open a conversation in a primary checkout or existing lane, use **+ New chat** in Agents or the **+** on its sidebar row. Cinderdeck automatically uses the first configured folder as the starting directory and gives the chat access to all workspace folders and files. Choose the provider and model in the chat; no folder selection is required. Saved launch requests retain their original starting directory when recovered.

Workspace roots can be ordinary folders containing repositories; Git at the workspace root is not required. Service warnings, changed settings for running services, and pending service/lane operation recovery do not block New chat. Chat validates the current workspace identity, revision and folders separately. An unavailable computer or invalid workspace shows the specific reason beside New chat with **Refresh workspaces** to reload the current context. Errors in Workspace settings must be corrected before opening a new chat.

Clicking a workspace in the sidebar opens **Agents** across its primary checkout and every lane. History uses saved workspace ownership, so removed lanes and older generations remain discoverable, including archived chats. Compact checkout labels identify each conversation; **Past checkouts** folds away removed checkout history and opens when filtered. Select a lane to narrow the list to its exact checkout. Conversations are paged 20 at a time, with search and status/provider filters applying to the displayed page. Archived conversations open directly for reading without restoring them to the active list. A conversation’s workspace breadcrumb returns to all workspace history even when its lane is gone. Explicitly deleted conversations stay deleted. Open one to continue its work or inspect its saved history. A finished turn means the agent has answered; it does not mark the feature complete. Connection state is shown separately, so a saved result can remain available while its provider is stopped.

If a launch reply is lost, use Check result or Retry saved launch. Cinderdeck keeps that launch request and its conversation identity across a page reload. Change the request only after Cinderdeck confirms it was refused or failed. Selecting another workspace does not move an existing conversation.

Agents are instructed to use `t3_worktree_handoff` for new-branch work from a primary checkout, unless the user explicitly requests an in-place branch switch. From the primary checkout this creates a native lane and moves the same conversation, preserving history and feature links. The thread directory and managed lane binding commit together; the provider detaches and the next turn uses the lane. Pass `continuationPrompt` to resume automatically. An existing worktree can be adopted with `adoptExisting: true`, its absolute `path`, and exact `branch`. New lane folders are chosen by Cinderdeck. Setup follows the native lane definition, and services remain stopped.

Handoff reads the current workspace and verifies its installation and physical repositories. A saved conversation's older native generation does not block the move when those identities still match; the request uses the live generation and revision. Temporary connection failures get one automatic retry of the workspace read, including destination verification. Lane creation and adoption are never automatically replayed. Unapplied settings, configuration issues, replaced repositories and installation changes report their specific recovery instead of asking for an ineffective connection refresh.

The conversation header identifies its lane or primary checkout and takes branch labels from the live native Git monitor, matched by physical repository identity. Shell `git switch` changes the current checkout branch; it does not move the conversation. Shell `git worktree add` or `cd` alone also does not transfer a conversation—use the handoff tool to register and move it. Uncommitted source files, existing terminal processes, and historical runs/recordings retain their original context. Other conversations sharing the primary checkout stay there. A pending or failed native creation leaves the chat in place and retains created files; retry the same request to recover its saved operation.

Agents share lanes and checkouts without claims or writer reservations. Native tasks and reviewers can start while another agent is active. **Stop agent** stops its provider process and preserves its conversation and lane; shared processes remain protected from stopping unrelated conversations.

**Schedule isolated review** opens a form for inspecting the source checkout's committed revisions, choosing a reviewer provider/model and instructions, and creating a separate reviewer lane. The source checkout must be clean; the feature can be an intermediate checkpoint. Scheduling attempts creation immediately, runs lane setup without starting services, and starts the reviewer conversation in approval-required mode. Reviewer lanes use a violet accent and a **Reviewer** label in the workspace sidebar, overview and lane map, including the native lane views. The generated reviewer name preserves that visual identity before agent status is available. If the inspected source changes before creation, inspect and schedule a fresh revision.

Native lane lifecycle API clients submit `lane.create`, `lane.adopt`, `lane.setup`, `lane.release` and `lane.remove` through the shared workspace backend and durable operation journal. Each method requires its own advertised native capability. Requests carry the reviewed installation, workspace generation/revision and a stable operation key; use the same key to inspect a lost reply. A resource that changes before dispatch is refused before effects. Workspaces exposes setup and removal in the selected lane inspector. Standalone Git worktree operations keep their existing cleanup guards.

The overview can filter the loaded contexts by search, activity, lifecycle and provider, and sort them by name or observed activity. The selected context stays in the inspector when its row is filtered out. Load another page to inspect its contexts; agent details that are unavailable keep a context visible rather than presenting an unverified match as empty.

Use **Selected context** beside Refresh to collapse or reopen the inspector. Drag its left edge to resize it, or focus the divider and use the left/right arrow keys (Shift for larger steps). Home and End select the smallest and largest widths; double-click resets the width. Cinderdeck remembers the width and visibility across workspace and lane changes. Narrow windows show the inspector below the overview, with resizing available when it returns to the side.

For a named lane, **Run setup** reports the actual setup result. **Remove lane** first reviews the affected worktrees and defaults to keeping their files. Deleting eligible managed worktrees and discarding ignored or changed copied files require separate choices. Cinderdeck checks active work, shared ownership and source changes before accepting removal. Check a saved request after a lost reply; its original lane and operation identity remain available across navigation.

The selected context’s **Pull requests** tab includes saved conversation links across its repositories and older contributors. Choose a PR to open the existing review and verification view, then return to the same workspace or Agents context. A replaced installation or lane generation keeps its saved identity visible and requires selecting a current context before inspection.

Setup receipts include the actual setup status and its operation attribution. A succeeded receipt means the native command returned a known result; inspect `result.setup.status` to determine whether setup passed. Release receipts identify the released lane and kept worktrees; removal receipts identify the removed lane and report removed/kept worktrees. Interrupted operations remain uncertain. Setup recovery reads only the state attributed to that operation, and a missing lane record does not establish that an earlier removal succeeded.


Connected lane API creation can pin repository-specific start revisions with `repositoryRefs: {"app": "<commit>", "api": "origin/main"}`. Each selected branch must be new. The native workspace resolves those revisions before creating anything and reports the pinned commits in the lane context; other repositories keep their defaults. This requires the advertised `operations.lane.create.repositoryRefs` capability. Missing capability or invalid input is a confirmed refusal; transport loss remains uncertain and must be checked through the original operation key.

The connected operation API can wait for a committed terminal receipt with `deckhand.operation.get({operationKey, waitMs})`, up to 25 seconds when the native peer advertises `operations.receipts.wait`. A timeout returns the latest pending/running receipt; it does not complete, cancel or repeat the operation. Continue recovery with the same key and signed-in actor. Omit `waitMs` for immediate inspection on older peers.

API clients can create a native lane and launch its conversation with `deckhand.session.create`. Keep the original operation key and request when retrying: Deckhand retains the lane and conversation identities if creation, setup, or provider intake is interrupted. `deckhand.session.create.get` only checks saved results and native receipts. An accepted result confirms conversation intake; inspect the session state for actual provider execution. This API requires native repository-start and receipt-wait capabilities; Workspaces exposes this flow through New feature.

A saved feature creation reappears when you return to its workspace, including after a reload or native generation change. Check result only inspects it; Continue saved request reuses its original scope and identities. If a lane was created but setup or intake failed, Review created lane keeps that checkout available. An uncertain result cannot be edited into a new request. Start another feature becomes available after a confirmed terminal result; it keeps the previous lane and conversation history. These controls currently use the shared web/desktop client; the separate mobile client remains an implementation gate.

New feature saves the feature and its intended workspace/repositories before asking Cinderdeck to create anything. A setup failure keeps that feature together with the lane and saved request. The returned creation receipt exposes `contextIntent`; the actual checkout and session are bound only after native creation is confirmed. The provider starts in the confirmed checkout after native creation.

Managed agent terminals can use [Cinderdeck CLI and MCP integration tools](cli-mcp.md) to inspect their saved lane, services, runs, recordings and evidence with the same domain validation as the UI.

If an evidence asset download fails from an older preparation, PR Verification offers Prepare a new bundle after that preparation is terminal. This explicitly saves a fresh operation key and keeps the previous immutable preparation receipt and error visible. Check preparation continues the current key; it never silently replaces an uncertain export.

### Connect during setup or in settings

The first-run setup offers **Connect to Cinderdeck** alongside the existing standalone computer, provider, and project flow. Choose an execution computer, inspect its verified Cinderdeck installation and host, then deliberately choose a workspace. **Open selected workspace** saves onboarding completion and opens that exact computer/workspace overview. It does not start services, import projects, or sign in to a provider. Provider accounts remain available in **Settings → Providers**.

**Settings → Integrations → Cinderdeck** shows a compact connection summary for the computer selected in the settings header. **Manage workspaces** opens that computer’s grouped workspaces and lanes in Settings → Workspaces; the integration section does not repeat the workspace picker. Expand **Connection details** for the last observed identity, protocol/channel and actual reported capabilities. **Refresh** performs discovery and identity checks. Pending operation receipts remain visible when they need attention: **Check status** reconciles the original operation key instead of creating replacement work, and **Review workspace** opens the original workspace when its identity is available. Missing computers and changed installation identities cannot silently switch to another computer.

**MCP & skills** shows the command-line prerequisite, then separate connection and skill status for each coding agent. Connect or reconnect MCP, install or update bundled skills, and optionally add the Claude Code mod. Expand **Setup details** for an agent’s configuration location, or **Setup options & included skills** for usage-note preferences and skill descriptions. Setup is disabled while loading, running an action, or showing a failed refresh’s last observed state.

### Shared lane creation sheet

Expand a workspace and press **+** beside Lanes or No lanes, or choose **Lanes → New lane** in its header. Manual creation, New feature, agent/CLI/MCP requests, and adoption all use the native creation sheet before creating worktrees. Agent-proposed names appear unchanged; otherwise a numbered lane name is supplied. Each repository shows a base selector and its current workspace branch. **Workspace settings → Folders → New lanes start from** saves independent defaults (`[repos.<id>] lane_from`), with `[lanes] from` and HEAD as fallbacks. Overrides in the sheet affect only that lane. Cancel leaves the workspace and worktrees unchanged. Managed feature intake follows the lane name and pinned commits returned by the reviewed native receipt.
